*图 1｜一个完整任务，需要连接需求、执行与验收。*

给一张商品图，让 AI 生成一张能直接上架的场景图。

这个需求看起来很简单。图片传进去，再加一句“你是一位专业产品摄影师”，剩下的交给模型。

但只要沿着这个场景往下想，问题很快就来了。

用户上传了三张图，到底用哪张？原图的背景要不要去掉？生成结果很漂亮，瓶身上的字却变了，能交付吗？工具报错了，模型还说“已经完成”，用户该相信谁？

这些问题，每一个都可能让一个看起来不错的演示，在真实使用中变成反复返工。

我觉得，提示词工程最值得认真讨论的部分，就在这里。

**我们得把“希望 AI 做什么”，写成一套任务，明确输入，也写清关键判断和完成标准。**

一句“你是专家”可以提供方向。但产品能不能交付，还要继续往下拆。

## 先把交付标准说清楚

“帮我分析一下竞品”和“给我一份能支持下周定价讨论的竞品分析”，需要的答案会很不一样。

前者允许模型自由选择范围。后者已经给出了用途，但还缺一些会改变结果的信息。

比哪些产品？关注套餐价格，还是付费转化路径？手里有什么资料？最后需要一张对比表，还是一个明确的定价建议？

这些细节会直接影响模型该查什么、怎么组织内容，以及哪些结论必须有依据。

所以写提示词之前，我会先问自己一个很朴素的问题。

**这份东西拿回来以后，我准备怎么用，又怎么判断它能不能用？**

回到商品场景图。所谓“好看”，其实容纳了太多解释。

换成“保留瓶身轮廓和商标，生成用于商品详情页的横版场景图，右侧预留文案区域”，模型可以遵循的要求就具体了很多。

再往前一步，还要约定：图片不清楚时怎么处理，多张参考图怎么选择，无法保持商标时是否交给人工检查。

这时候，提示词开始接近一份真正的任务说明。

![目标、输入、约束与验收](</assets/images/prompt-engineering/02-brief.png>)

*图 2｜把模糊愿望拆成可以检查的任务要求。*

角色仍然有用，但角色得和任务连接起来。告诉模型“你是产品经理”，不如继续补上“这份分析用于决定首版做什么，团队只能承担一个月开发，已有能力包括哪些”。

用户背景也值得写。面对刚入行的人和负责立项的人，同一个技术概念，需要解释的深度并不相同。

如果文字很难说清想要的颗粒度，就给一两个合格例子。这是 Few-shot 的实用价值：让模型看见你认可的结果长什么样。

不过，例子也会影响模型的选择范围。只给顺利案例，它可能学会了格式，却依然不知道遇到缺失信息该怎么办。一个“信息不足，先澄清”的例子，有时比再加一个完美答案更有用。相关做法也可参照 [Anthropic 的提示词实践](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)。

## 指令放在哪里，也是一项产品设计

一个商品图片助手，可能每天处理不同商品，但始终需要遵守相同的交付规则。

这类稳定规则适合放进系统层配置。用户这次上传的图片、希望换成的场景，则属于当前任务。

System Prompt 负责相对稳定的行为约束，User Prompt 表达当前需求。具体平台如果还有 developer 等消息角色，就按照它自己的消息规范来设计。

有些资料会再引入 Meta Prompt。这个词在不同语境里含义并不统一，有时指生成或优化提示词的方法，有时泛指更上层的约束。直接把它当成所有模型都共有的最高权限层，容易把产品设计带偏。

还有一个很容易忽略的细节。

你在聊天框里写“下面是系统提示词”，这段话仍然来自用户消息。文字上的命名，并不会改变它实际所在的位置。

同样，系统指令的优先级，也不能替代程序里的权限控制。写一句“禁止读取别人的文件”，还需要后端真正限制文件访问范围。

![指令分层与执行权限](</assets/images/prompt-engineering/03-instructions.png>)

*图 3｜外部资料提供信息，执行权限仍由系统校验。*

指令之外，模型还需要工作材料。这就涉及 Context，也就是它这一次生成时实际能看到的信息。

对话历史会占空间，检索片段会占空间，工具返回的长文本也会占空间。Token 是衡量这些内容的一种单位，和中文字数没有固定的一一对应关系。

**上下文管理，要决定哪些信息值得留下。**

用户已经确认的商品、必须保持的属性，以及最新一次处理结果，应当清楚地保留。过期方案和重复报错则可以整理，避免后面的任务一直背着前面的混乱。

跨会话记忆也需要产品实现保存和重新提供信息。重新打开一个窗口，模型不会天然带着所有旧对话继续工作。

所以，“第一条提示词一定决定全局”更适合当作提醒自己整理需求的习惯。实际效果还要看消息层级，以及每次调用究竟送进去了什么。

![上下文与长期记忆](</assets/images/prompt-engineering/04-context.png>)

*图 4｜当前可见的信息与持久保存的信息，需要按需衔接。*

## 缺知识，缺能力，得分别处理

模型答得不好，原因可能差得很远。

假设你让它回答“今年公司差旅报销有什么变化”。如果它没拿到公司制度，再强调十遍“准确回答”，也无法凭空补出可靠依据。

这类问题适合考虑 RAG，也就是检索增强生成。

系统先从外部资料里找到相关内容，再交给模型组织答案。Embedding 可以把文本变成向量，帮助检索语义相近的内容；关键词检索也能参与，实际应用可以结合使用。

但“搜到了”还不等于“找对了”。

假如候选材料里同时有员工福利、旧版报销办法和新版差旅制度，Rerank 可以对这批候选重新排序，让与当前问题更相关的材料排在前面。

Rerank 只能处理已经召回的候选。新版制度根本没进入候选集，后面排得再认真，也找不回漏掉的证据。这几个环节的分工，可以参照 [Contextual Retrieval 的说明](https://www.anthropic.com/engineering/contextual-retrieval)。

文档的生效日期、适用地区和员工权限，也需要系统处理。模型面对两份互相矛盾的制度，不能只凭哪段文字更像答案来选。

RAG 提供了补充外部知识的路径，但它仍然可能检索错误，生成时也可能误读资料。答案带了引用，还要看引用是否真的支持结论。

![检索、重排与有依据的回答](</assets/images/prompt-engineering/05-rag.png>)

*图 5｜重排处理已有候选；知识是否有效、答案是否有依据，还要分别检查。*

另一些问题，更接近稳定行为。

例如同一套电商业务里，售前要帮助比较商品，售后要先核实问题再推进处理。提示词和示例可以先建立基线；如果任务足够高频，积累了高质量数据，现有方式仍达不到要求，才值得进一步评估微调。

这里有一组术语需要分开看。

SFT 描述用监督式输入、输出样本训练模型；PEFT 描述参数高效的调整方法。它们处在不同维度，可以组合。使用 LoRA 等方式做监督微调，就是一种可能的组合。[Hugging Face 的 SFT 文档](https://huggingface.co/docs/trl/en/sft_trainer#train-adapters-with-peft)也给出了这类实现。

我更愿意从失败原因来做选择：任务没有讲明白，先改指令；缺少最新知识，补资料和检索；需要稳定学习某种行为，再评估训练的收益。

这些办法可以一起使用。每加一层，都应当知道它具体解决了什么问题。

![按失败原因选择优化方法](</assets/images/prompt-engineering/06-methods.png>)

*图 6｜三种方法可以组合，但每一层都要有明确用途。*

## 真正执行任务，要把工具接起来

再回到开头的商品图。

用户需要的是最终图片。让模型描述一遍“我会先抠图，再生成场景”，任务还没有完成。

一条可执行的路径，至少要串起这样的过程：接收图片，确定当前操作对象，按要求判断是否需要抠图，再调用场景生成能力。结果回来后，还要检查主体与商标是否保持、尺寸是否合规；不合格就按约定重新处理，或者转交人工确认。

Tool Calling 就发生在这条路径里。

模型根据工具描述，提出调用哪个工具、传什么参数。外部程序检查请求并执行，再把结果交回来。模型随后可以继续调用工具，或者向用户解释结果。

所以设计工具时，光取一个好名字还不够。

工具适合什么情况？输入是原图地址，还是已经处理过的图片地址？失败会返回什么？超时以后能不能重试？这些都要有明确约定。

比如统一使用 original_image 和 prepared_image 两个字段，分别表示原始图片与可用于生成的图片，就比在长对话里反复说“用刚才那张”清楚得多。

原图已符合工具输入要求，可以直接成为 prepared_image；需要抠图，就等抠图成功后再更新这个字段。多张图则要有各自的标识，不能把上一张商品的结果误传给下一步。

![商品图处理与验收流程](</assets/images/prompt-engineering/07-tool-calling.png>)

*图 7｜从输入到验收的流程示意；生成结果还需检查主体和规格。*

这里也能顺便看清 API、Tool 和 MCP 的关系。

API 是系统提供的调用接口。Tool 把某项能力整理成可调用的工具，内部可能调用 API，也可能运行本地函数。MCP 提供标准化连接方式，让 AI 应用发现并使用服务端提供的工具等能力。

一个 MCP Server 可以提供多个工具。具体什么时候用、先用哪一个，仍然需要模型或工作流来决定。这是依据 [MCP 架构规范](https://modelcontextprotocol.io/specification/2025-06-18/architecture)作出的职责归纳。

![MCP连接架构](</assets/images/prompt-engineering/08-mcp.png>)

*图 8｜请求与结果沿连接双向传递，具体调用由宿主侧协调。*

选择哪种连接方式，要看系统现状和接入需求。仅凭 API、Tool 或 MCP 的名字，排不出一张通用的稳定性榜单。

如果处理顺序已经确定，就可以把关键步骤固定在工作流里；需要根据输入判断的部分，再给模型相应空间。

**模型负责提出合适的调用，系统负责鉴权、执行与结果校验，并处理失败。**

尤其涉及真实业务动作，权限和参数校验得落到程序里。密钥放在后端，工具失败就返回失败，不能让一段流畅的回答替代实际完成状态。

## 让模型多想，也得有目的

遇到复杂问题，我们经常会给模型补一句“请一步一步思考”。

CoT，也就是思维链，强调通过中间推导帮助完成任务。它的价值要看这些中间步骤，是否真的有助于得到更可靠的结果。

给商品分类、筛选构图方案时，可以分别考虑合适的拆解方式；工具的前后依赖也一样。但把任何答案都拉长，未必有收益。

产品里更值得要求模型交付的，是可核查的信息：用了哪些材料，依据什么条件作出判断，还有哪些地方不能确定。

一段写得完整的解释，并不能证明它真实反映了模型内部的推理过程，也不能自动证明结论正确。[CoT 原论文](https://arxiv.org/abs/2201.11903)讨论了中间推导的作用；[Thinking 文档](https://platform.claude.com/docs/en/build-with-claude/thinking)则说明了可见摘要与实际思考的区别。

是否增加推理预算，需要放进任务里测。复杂分析可能值得等待，简单的字段提取则要关注额外耗时有没有带来收益。

![按任务分配推理预算](</assets/images/prompt-engineering/09-reasoning.png>)

*图 9｜根据任务难度选择处理路径，再检查额外推理带来的收益。*

多模态任务同样需要这种克制。

已经给了参考图，文字可以重点交代动作和镜头变化，再明确哪些属性必须保持。没必要默认把图里每个细节重新描写一遍。

比如商品场景图希望营造清冷感，可以补充冷色光线、留白和物体间距，让抽象要求对应到可观察的选择。

这是一种提高可控性的办法，不能据此断言模型完全无法处理情绪概念。描述要写到什么程度，仍然需要结合模型和素材测试。

## 把 Prompt 当成需要验收的产品配置

写完之后，最容易让人误判的一步，是拿自己熟悉的几个例子试一下，感觉不错，就准备上线。

但用户会带来完全不同的输入。

商品图可能模糊，用户可能临时改主意，参考图片里可能夹带无关文字。工具也可能超时，返回空结果，或者只完成了一半。

这些情况，得进入测试集。[评估设计文档](https://platform.claude.com/docs/en/test-and-evaluate/develop-tests)也强调先明确成功标准，再检验输出。

对商品图助手，我会分别检查任务能否走完、指定主体是否保持，也看结果是否满足交付规格，以及用户需要返工多少次。对知识问答，则要检查有没有找到正确证据，结论是否受到证据支持，资料不足时是否会明确说明。

指标必须跟着任务走。

生成了一段 JSON，可以检查结构是否合规；但结构正确，不代表里面的商品价格就是真的。能调用工具，也不代表调用的对象和顺序都对。

比较两个 Prompt 版本时，应尽量固定模型与输入材料，也固定工具环境和关键参数。测试集里既有常见任务，也有重要边界，才能知道某次修改是在普遍改善，还是只照顾了一个样例。

随后再看成本。

一次调用更便宜，如果导致用户重试更多次，最终未必划算。把人工返工也算进去，才能接近一次合格交付的真实成本。

版本管理则让这些判断能够留下来。

每次准备发布的新版本，记录改了什么、为什么改，同时记下测过的案例，以及谁确认上线。真出了问题，能够找到对应版本并回退。

团队早期用一张清楚的表配合版本记录，也可以把这件事做起来。关键是让文本、测试结果和线上状态对得上。

![提示词版本评估与发布](</assets/images/prompt-engineering/10-evaluation.png>)

*图 10｜版本、测试结果与线上状态要对应，出现退化时能够回退。*

我觉得，这也是 AI 产品经理值得花时间建立的能力。

从一个用户需求里，判断应该补哪些信息，哪些步骤可以交给模型，哪里必须有系统约束，以及什么结果才算交付完成。

下一次打开输入框，可以先写下任务的验收标准。

再开始写那句“你是一个……”。
