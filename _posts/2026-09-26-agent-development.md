*图 1｜能执行只是起点，交付前还需要检查与判断。*

一张图片传进去，几张不同尺寸的图片出来。

如果只看演示，一个多尺寸图片 Agent 的功能似乎已经完成了。能理解需求，能调用工具，最后还有成品。

但在一个设计案例里，早期版本选择了更彻底的自动化：用户上传图片后，直接生成一整套尺寸。

问题也跟着来了。用户还没选要哪些图，积分已经消耗了。系统忙得很认真，做出来的却可能有一些用不上。后来的方案加入了选择环节，让用户先确认尺寸，再开始生成。

这个改动很小，却把一个容易被忽略的问题摆到了桌面上。

**Agent 能完成动作以后，产品还要决定，它应该在什么条件下开始，又在什么地方停下来。**

模型、提示词和工具当然都重要。但用户面对的，是从输入到交付的一整段经历。少问一个必要的问题，多跑一次不需要的生成，都会直接变成他的时间和费用。

## 先让用户知道，会得到什么

做多尺寸图片工具，可以先把承诺收窄到一件具体的事：根据用户选定的比例，调整已有图片，并尽量保持主体与风格。

这个承诺里，每个词都影响后面的设计。

“已有图片”意味着原图是必填输入；“选定比例”意味着生成范围得明确；“保持主体”则意味着不能只检查文件有没有生成，还要看人脸、商标和文字是否被改坏。

界面也要表达这些要求。

需要图片，就把上传区域放到显眼的位置，说明支持的格式。素材缺失或者无法读取时，先告诉用户补什么。不能一边把页面做成随便聊的样子，一边在后台指望模型猜出每一个必要条件。

选择比例同样可以做成几个清楚的选项。用户已经明确具体比例，或者认可默认规格，就直接处理；没有说清楚，再用选择题补足信息。

这里要区分“没回答”“跳过”和“取消”。它们不天然等于同意生成全部尺寸。默认方案若会消耗额度，应当在执行前让用户知道它的范围和代价。

我觉得，判断这类交互值不值得加，可以看它能否改变后面的动作。真正影响生成数量、费用或者最终用途的信息，值得确认；用户已经讲清楚的内容，就不要换个说法再问一次。

**好的输入设计，会提前减少一部分模型需要处理的不确定性。**

*图 2｜先确认必要输入与执行范围，减少无效生成。*

## 把一件事做完整，再扩展范围

给 Agent 起一个“全能设计专家”的名字，很容易。明确它这次到底负责什么，反而需要做取舍。

多尺寸适配工具，可以只负责处理已经存在的素材。用户要重新设计品牌、生成视频，就说明当前范围，给出下一步入口。不能因为图片已经上传，就无视用户的新意图，继续扣费执行旧任务。

检查一个单 Agent 是否设计完整，我会看六个方面。

它有清楚的目标和能力边界吗？所需工具真实存在、已经接通了吗？输入与输出有没有明确约定？什么时候结束？这些环节能不能组成一条完整任务链？

这是一份实用的检查清单。目标集中，依然可以包含多步操作；预先设计好的暂停或人工接手，也可以是合理的结束状态。

![单Agent任务的六项检查](</assets/images/agent-development/03-closed-task.png>)

*图 3｜六项检查帮助收窄范围，检验任务是否完整。*

“自主”需要放在这样的边界里理解。

模型可以根据当前情况，决定是否需要补信息、调用哪个工具，再判断拿到结果后继续做什么。应用则负责把权限、预算和执行限制落实下来。

确定的部分也可以固定。比如输入文件校验、输出尺寸检查，没有必要每次都让模型重新推理一遍。工作流能够包含条件分支，也能和模型的动态判断一起使用。[Anthropic 对工作流与 Agent 的区分](https://www.anthropic.com/engineering/building-effective-agents)也强调了这种控制方式的差别。

所以架构选择要回到任务：哪些步骤真的需要理解和判断，哪些规则已经足够确定，可以交给程序执行。

## 出了问题，先看它错在哪

假设图片生成了，但画面里的商品变形了。

再假设图片根本没有生成，因为传给工具的原图地址为空。

这两种失败，用户都可能用一句“不好用”来反馈，处理办法却完全不同。

前一种先检查生成模型实际收到的原图、处理要求和参数，再看模型能力与验收目标是否匹配。后一种则要回到执行记录，检查图片从上传到调用之间究竟在哪里丢失。

这就是排查 Badcase 时很有用的一次拆分：生成质量出了问题，还是执行链路出了问题。

![生成质量与执行链路的失败归因](</assets/images/agent-development/04-badcase.png>)

*图 4｜先区分失败位置，再决定改提示词、工具还是执行逻辑。*

继续往下，还可以区分具体原因，其中既有理解或工具选择错误，也可能是参数缺失、外部服务超时。把失败定位到具体一步，团队才知道该改什么。

只给 System Prompt 加上一句“务必认真”，通常解释不了这些差别。[工具工程实践](https://www.anthropic.com/engineering/writing-tools-for-agents)也强调查看实际调用与返回信息，再用评估验证修改效果。

提示词本身当然要检查。尤其是长期迭代的版本，可能前面要求“生成后立即结束”，后面又要求“详细说明每张图”；一个位置要求用户确认，另一个位置却允许默认全部执行。

冲突积累多了，继续加粗和重复，未必能解决问题。

我会先保留当前版本和对应失败样例，整理有效规则，再决定局部修改还是重写。新版本看上去更简洁，也要和旧版本跑同一批测试，才能知道它有没有变好。

一份面向执行的 System Prompt，至少要把三部分讲清楚：可用工具及使用条件，包含分支的工作流程，以及交付要求和终止条件。

比如，缺图片时请求补充，比例确认后才能创建任务，工具报错时进入哪条分支，已经完成的结果怎样保留。

这几句话，比把角色头衔再写长一点，更接近实际工作。

![工具、工作流程和完成标准](</assets/images/agent-development/05-system-prompt.png>)

*图 5｜能力、步骤与完成标准，需要在执行规则中对齐。*

## 工具交接，不能靠“你应该懂”

多尺寸图片 Agent 的一个关键细节，是原图与生成要求必须正确传给工具。

假设工具接口规定，原图放在 `image_url`，处理描述放在 `prompt`。那么，只在自然语言里写一句“参考刚才那张图”，并没有完成这次参数传递。

要查的是实际请求里有没有原图，指向哪张图，比例参数又是不是用户最后确认的那个。

多轮对话尤其容易在这里出错。用户先要横版，后来改成竖版；先传了旧海报，又换了一张新素材。如果每一步都自行解读整段聊天历史，后面的工具可能拿到不同版本的需求。

可以把当前有效需求整理成任务状态，明确记录原图标识、目标比例，以及用户确认过的限制。新要求来了，更新相应字段；已经失效的要求不再继续参与执行。

字段名本身没有魔法。真正起作用的是大家引用同一份状态，并且传参前有校验。

![状态字段与工具参数的正确对应](</assets/images/agent-development/06-fields.png>)

*图 6｜明确当前图片、有效需求与目标比例，再传给工具。*

Tool List 也应当和实际能力一致。除了名称，还要说明用途、必填参数与返回结构，并约定失败怎么表达。在提示词里写出一个工具名，并不会自动把这个工具接入系统。[工具定义文档](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)可以帮助核对这些接口要求。

MCP 则负责标准化连接。一个 MCP Server 可以提供多个 Tool，工具内部可以调用 API，也可以执行本地逻辑。连接建立后，业务权限和参数检查仍然需要实现。相关职责可以对照 [MCP 架构规范](https://modelcontextprotocol.io/specification/2025-06-18/architecture)。

还有一个很实际的选择：到底要不要并行。

几个尺寸都基于同一张原图，需求已经确认，任务之间互不依赖，就可以评估并发生成。若后一步需要前一步的结果，就得等待。服务限流和预算，也会限制同时启动多少任务。

并行有机会缩短等待，但不会让所有调用变成免费，也不能保证总耗时永远等于一张图的耗时。

失败处理也要有分寸。临时超时可以考虑有限重试，输入缺失就先补参数；权限不足，应当停止并说明原因。备用工具要经过能力和权限检查，不能把切换工具当成绕过拒绝的办法。

如果三张图已经完成，两张失败，可以保留成功结果，把失败项目明确列出来。用户决定继续时，再处理缺的部分，避免整套重跑。

**有出口的失败，比一边不断重试、一边持续消耗额度，更容易让人信任。**

![受控并发、有限重试与人工出口](</assets/images/agent-development/07-parallel-fallback.png>)

*图 7｜任务分支示意：保留成功结果，为失败项目设置明确出口。*

## 多 Agent 的收益，要算上交接成本

流程越来越复杂以后，拆成多个 Agent 很自然。

比如，一个负责需求分析，一个专门生成图片处理方案，再由协调者收集结果并推进执行。

这类分工有实际价值。专业规则可以分开维护，能够独立完成的任务也有机会并行，单个执行单元不必携带所有细节。

但信息不会因为换了一个 Agent，就自动完整地传过去。

子任务收到的是哪版需求？图片标识有没有带上？返回的是草稿、已验证结果，还是失败说明？协调者发现两个结果冲突，由谁处理？

这些交接都需要设计。

如果拆分以后，多个 Agent 还要不断交换同一大段上下文，或者后一步始终等前一步，收益可能抵不过额外调用与协调成本。[多 Agent 研究系统的实践](https://www.anthropic.com/engineering/multi-agent-research-system)也说明了任务可拆分性与协调成本的重要性。

我会先建立一个足够简单的基线，再看复杂度是卡在什么地方。规则互相干扰，还是上下文太重？存在可以独立处理的专业子任务，还是只是觉得多 Agent 听起来更高级？

找到具体瓶颈后，再用同一批任务比较拆分前后的质量、延迟和成本。

![单Agent与多Agent的架构取舍](</assets/images/agent-development/08-single-multi.png>)

*图 8｜专业分工可能带来收益，也会增加信息交接与协调。*

用户没有义务为架构的热闹付费。

他只会感受到，这个任务是不是更快完成了，结果是不是更可靠了。

## 用户看到的进度，要对应真实工作

长任务不能只留一个不断转动的图标。

“正在确认尺寸”“正在生成横版”“竖版生成失败，可以重试”，这些信息能够帮助用户判断要不要继续等，以及接下来需要做什么。

但计划和事实要区分。模型说“准备生成三张图”，只能说明下一步安排；工具返回成功，文件确实可用，并且通过该阶段约定的检查，才可以把对应任务标成完成。

内部需要保留足够细的记录来排查问题。用户界面则应使用他能理解的语言，必要时提供可查看的结果和依据。密钥不能暴露，内部字段也不必全部堆到进度条下面。

遇到部分完成，就显示部分完成。转人工接手时，带上已经确认的需求和已产出的结果，减少用户重新解释的负担。

这类状态设计，往往比多一段热情的回复更有帮助。

![真实执行状态驱动用户可见进度](</assets/images/agent-development/09-progress.png>)

*图 9｜计划、部分完成和全部完成，应当对应真实执行状态。*

## 上线前，要回答三个不同的问题

这个 Agent 能不能跑通？结果是不是正确？换一些输入、多运行几次，表现还稳不稳？

三层都值得分别验证。

跑通，要看该走的流程能否走完，工具与结果是否可用。做对，要检查图片比例和主体一致性，也要看是否遗漏用户要求。稳定，则需要覆盖模糊输入、素材缺失和服务异常，再看重复运行时是否会偶发失误。

![功能、质量与鲁棒性的三层验收](</assets/images/agent-development/10-acceptance.png>)

*图 10｜流程、结果和异常处理，需要分别验收。*

一张“黄金样例”，还需要配套的验收方法。

一张漂亮的参考图可以帮助团队对齐审美，但验收还需要测试输入、评分规则和运行条件。否则大家拿着不同的样本，最终很难判断谁说的“更好”成立。

指标可以先抓住四个。

任务完成率，看约定的任务有没有完整交付；工具调用准确率，检查该调用的是否调用，也检查不该调用的有没有误调用；输出合格率，看交付物满足要求的比例；重复运行稳定性，则观察同样输入下结果的波动。

分母和失败口径要提前约定。把失败任务删掉，只统计已经生成的图片，会让数字好看，也会掩盖用户真正遇到的问题。

调用成本与端到端耗时也要一起看。开放式图片质量可以结合人工评审，尺寸和文件可读性等明确要求则适合程序检查。[Agent 评估方法](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)强调同时检查执行过程与实际结果，而非只相信模型的完成声明。

不存在适合所有业务的“成功率达到某个数字就能上线”。普通创作任务与会修改业务数据的任务，失败代价差得很远；少量顺利样本，也无法证明异常情况已经得到覆盖。

这些约定，应该进入需求文档。

从目标用户和输入输出写起，接着补上分支流程与工具要求，再保存测试样例、评分规则和版本记录。研发拿到以后，能知道该实现什么，测试能判断是否达标，产品也能解释为什么发布。

修改先进入测试环境，验证后再按风险逐步发布。出现退化，要能找到对应的提示词、模型及工具配置，恢复稳定版本。

走到这里，一个 Agent 才开始具备持续服务用户的条件。

我觉得，AI 产品经理值得建立的能力，就是沿着一次任务，看见所有容易被忽略的交接。

什么时候该问，什么信息不能丢，失败后怎么继续，以及最后凭什么说“完成了”。

把这些小事逐个做对，用户才有可能放心，把下一次任务也交过来。
